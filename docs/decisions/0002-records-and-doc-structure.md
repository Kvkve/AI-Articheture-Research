# 0002 Records: a short rule file, a status file that is rewritten, a few decision records

- Status: Accepted
- Date: 2026-11-23

## Background

Every session starts with an empty context, and long conversations get compressed. So the state of the project must live in the repository. But an AI tends to keep creating new documents. Over time nobody reads them, and outdated ones mislead later work.

## Options

1. Adopt a ready-made spec-driven process: each feature gets its own set of requirement, design and task documents.
2. Define a small fixed structure: rule files, a status file, a task list, decision records, research, learning notes.
3. No fixed structure. Write whatever is needed at the time.

## Decision

Option 2. The structure is the document map in `AGENTS.md`. Rules live in `AGENTS.md`, which every AI tool can read. `CLAUDE.md` imports it and adds rules for Claude Code. `README.md` holds the project background. `docs/decisions/README.md` is the index of decisions.

## Reasons

- Independent reviewers found option 1 verbose and a cause of document sprawl. It is too heavy for a one-person project.
- Option 3 is the situation this decision is meant to prevent.
- A rule file should be written by hand and kept short. Measured data shows that rule files generated by an AI lower task success slightly and raise cost by about 20%. Only content the AI could not work out by itself helps.
- The status file is rewritten in full, not appended to, so it does not become a log nobody reads.
- `AGENTS.md` is used so that a model from another vendor can read the same rules when it reviews the work.

## Costs and safeguards

- Two rules have no evidence for or against them and are inferences: "a lesson must become a check or a rule", and "no new documents outside the map". Look back after some use to see whether they work.
- For now these rules are only words. When the first code arrives, turn what a machine can judge into automatic checks, including a check that every path in the document map exists.
- Rule files grow over time. Prune them at the end of each milestone.
- Decision records can mislead later sessions if they go out of date. The safeguards are the status field, the rule that a new decision marks the old one "Superseded" in the same change, and the review at the end of each milestone.
